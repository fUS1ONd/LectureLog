# Извлечение релевантных кадров из видео лекций — дизайн

Дата: 2026-07-05. Статус: дизайн согласован с пользователем, перепроверен; план
реализации НЕ написан (следующий шаг — `superpowers:writing-plans` в новой сессии).

## 1. Задача и ограничения

Видео лекции → отбор релевантных стопкадров + привязка их к секциям конспекта.
На входе уже есть: транскрипт SRT с таймкодами и секции structurize с
нормализованными start/end (коммит `6c535d2`).

Типы лекций (пайплайн обязан работать со всеми):

- **доклад со слайдами** — брать слайды, игнорировать спикера;
- **препод у доски** — брать доску в момент «дописал», до стирания, без перекрытия
  спикером;
- **live-coding** — ловить осмысленные точки остановки, а не промежуточный набор;
- **смешанные**.

Жёсткие ограничения: **центы за 1.5 ч видео** (нельзя per-frame VLM) и **минуты на
VPS без GPU** (ориентир: 4 vCPU).

Зафиксированные с пользователем решения (не переспрашивать):

- проектируем как стадию lecturelog-core, не standalone;
- VLM преимущественно на бесплатных BYOK-ключах; рабочая лошадка —
  `google/gemini-3.1-flash-lite` (~500–600 RPD на ключ, RPM 15); платную цену по
  OpenRouter считаем для контроля;
- плотность: **только осмысленные кадры** — секции «говорящей головы» остаются без
  кадров, это норма;
- guide-режим («видео → текстовый гайд») — ОТДЕЛЬНЫЙ дизайн позже; здесь только
  точки расширения (§12).

## 2. Переосмысления постановки

1. **Привязка — не отдельная задача.** Кадр рождается с таймстемпом; привязка =
   поиск секции по интервалу + монотонизация (аналог `normalize_slide_mapping`).
   LLM-матчинг нужен только документным слайдам (у них нет таймкодов).
2. **Для доски «выбрать кадр» — неправильная рамка.** Лучший кадр «дописал» часто
   не существует в видео (препод перекрывает доску). Стопкадр доски
   **синтезируется** из background model (§5.D1) — реконструкции доски без человека.
3. **«Не покадрово через VLM» ≠ «VLM только в конце».** Ошибка — VLM *в цикле*.
   Две дешёвые точки касания (классификация режимов + финальный QC) = ~5–10
   батч-запросов на лекцию: бесплатно на BYOK, доли цента платно, а робастности
   дают больше, чем любые эвристики.

## 3. Отвергнутые альтернативы

| Подход | Почему нет |
|---|---|
| Чистый CV без VLM | Классификация сцены и фильтрация мусора на эвристиках хрупкие; заставки/«no signal»/крупные планы спикера не отсеять надёжно. |
| Per-frame VLM (даже 1/30 с) | Дорого, медленно; главное — VLM без временнóго контекста не видит «дописал» и «точку остановки»: это события во времени, а не свойства кадра. |
| Нативный видео-вход Gemini («дай таймстемпы») | 90 мин ≈ 0.5–1M токенов даже в low-res; free tier не влезает, точность таймстемпов низкая, видео-вход через OpenRouter ограничен. Возможный будущий fallback. |
| Локальные NN (YOLO/CLIP/OCR) | Зависимости и CPU; всё достижимо дешевле: спикер = движение, семантика = VLM за копейки. OCR — опциональное усиление code-режима позже. |

**Выбрано: трёхслойная воронка «сигналы → режимы → политики»**: локальный CV
считает временные сигналы по всему видео; VLM подключается дважды точечно.

## 4. Архитектура (обзор)

```
видео (на диске после ingest)
  │
  ├─ A. Грубый проход: ffmpeg 1 fps ~320px → сигналы на кадр (numpy)
  ├─ B. Сегментация таймлайна на РЕЖИМЫ по сигнатуре сигналов
  ├─ C. VLM №1: классификация режимов + bbox рабочей области (1–2 вызова)
  ├─ D. Пер-режимные политики отбора кандидатов (локально) → ~20–60 ts
  ├─ E. Качественная выемка стопкадров (full-res, точечные seek)
  ├─ F. VLM №2: QC + подписи (2–4 вызова) → финальный набор
  └─ G. Привязка ts → секция structurize + монотонизация → экспорт
```

Ключевое решение: **в режиме конспекта кадры НЕ влияют на структуризацию**
(в отличие от старого `video_slides`, где слайды шли в slide_match). Structurize
работает от транскрипта, кадры привязываются пост-хок → стадии развязаны, и стадию
кадров **можно исполнять параллельно со structurize** (wall-clock прирост почти
нулевой). Зависимость D от SRT удовлетворена после transcribe.

Это свойство режима конспекта, а НЕ инвариант порта — см. §12.

## 5. Стадии подробно

### A. Грубый проход и сигналы

Один проход ffmpeg: `-vf fps=1,scale=320:-2`, rawvideo gray в пайп → numpy;
параллельно мини-цвет (для цветостатистики) и JPEG-тумбы на диск (~20 КБ × 5400 ≈
100 МБ, чтобы шаги C/D выбирали кадры без ре-декода).

Сигналы на кадр (все дешёвые, суммарно < 1 мин на 5400 кадров):

- `dhash` (8×8) — грубая идентичность содержимого;
- `mad` — средний abs-diff с предыдущим кадром;
- `motion_mask` — бинаризованный diff, дилатированный (где движется);
- `edge` — плотность градиентов (Sobel) — «сколько контента»;
- `shift` — глобальная трансляция (phase correlation) — панорамы/скролл/едущие доски;
- цветостатистика — насыщенность, грубая гистограмма тонов (мел/маркер/слайды).

### B. Сегментация на режимы

Оконные статистики (окно ~30 с) над сигналами A:

- доля кадров-плато (`mad < t_low`), частота ступенек (`mad > t_high`),
- доля мелких локализованных диффов (печать), величина `shift`,
- тренд `edge` (накопление ink).

Границы режимов — где вектор оконных статистик сдвигается (порог/гистерезис;
change-point detection типа PELT — опционально, v1 обходится правилами). Сегменты
< 20 с сливаются с соседями. Каждому режиму — предварительный тип по сигнатуре:
ступеньки+плато → `slides`; монотонный рост edge → `board`; частые мелкие диффы →
`code`; большой `shift`/хаос → `camera`; ничего → `speaker`.

### C. VLM №1 — классификация режимов

По 1 репрезентативному кадру на режим (самый резкий из 3 сэмплов середины режима),
батчем ≤ 16 картинок, JSON-mode:

```json
[{"idx": 1, "type": "slides|board|code|terminal|speaker|other",
  "content_bbox": [x, y, w, h], "board_kind": "chalk|marker|none"}]
```

`content_bbox` (нормализованный) калибрует ROI для ink-метрик и кропов. Если bbox
неправдоподобен (площадь < 10 % или выходит за кадр) — fallback на полный кадр.
Режимов у 1.5 ч лекции обычно 5–20 → 1–2 вызова. VLM-тип уточняет/перебивает
предварительный тип из B (временнáя сигнатура остаётся тай-брейкером: «слайды с
кодом» не печатают — если VLM сказал `code`, а диффов-печати нет, это `slides`).

### D. Политики отбора кандидатов

#### D1. Доска: «дописал»

Фундамент — **background model с гейтом по движению** (а не наивная медиана: она
ломается, когда препод стоит на месте дольше полуокна). Пиксель модели обновляется
только если в нём нет движения K≈5 кадров подряд (при 1 fps ≈ 5 с); неподвижный
препод «замораживает» свой участок в последнем честном состоянии доски, а не
портит его. Все метрики — **по модели, не по сырым кадрам** (иначе вставший перед
доской препод выглядит как стирание).

- `ink(t)` = штриховые пиксели ROI после нормализации освещения (деление на сильно
  размытую версию) + адаптивный порог; полярность (светлое-на-тёмном для мела /
  тёмное-на-светлом для маркера) — из `board_kind` шага C.
- **Пишет**: d(ink)/dt > 0 устойчиво + motion рядом с зоной прироста.
- **«Дописал»** (кандидат): ink стабилен (|Δ| < ε) ≥ 10–15 с И motion ушёл из
  свеженаписанной зоны — препод отошёл.
- **Стирание**: Δink < −30 % за < 5 с по модели → зафиксировать последнее
  стабильное состояние до падения (оно уже в модели, гарантированно без человека).
  Гистерезис против частичных стираний и «стёр-и-сразу-пишет».
- **Новизна**: снимать только при ≥ 20 % нового ink с прошлого снимка либо на
  границе режима — иначе десять копий одной доски.
- **Едущие доски / панорамы**: `shift` выше порога = граница поверхности, модель
  сбрасывается, накопленное состояние фиксируется как кандидат.

#### D2. Live-coding: «точка остановки»

Code-режимам 1 fps мало: их отрезки **передекодируются на 3–5 fps** (декод только
активных сегментов — дёшево, см. §8).

- **Печатает**: непрерывные мелкие локализованные диффы в ROI редактора. Курсорное
  мигание отсекается по площади (< 0.05 % кадра, один мелкий bbox, ~1 Гц).
- **«Точка остановки»** (кандидат) = тишина ≥ 4–5 с после edit-burst ≥ 8–10 с.
- **Буст**: в ≤ 15 с следует переключение окна (резкая смена layout) или изменения
  в output-панели — паттерн «написал → запустил», самый сильный сигнал
  завершённости. Тогда снимается **пара**: код до переключения + вывод после.
- **Транскрипт — бесплатный оракул**: словарь триггеров («запустим»,
  «скомпилируем», «сохраняем», «вот и всё», «смотрите, что получилось») в окне
  ±10 с бустит кандидата. Без LLM — SRT уже есть.
- **Скролл**: вертикальный `shift`; середина скролла — не кандидат. Если после
  кандидата код только дорос (diff = добавленные строки при том же скролле) —
  поздний вытесняет ранний.
- Автокомплит/нотификации (< 2 с оверлеи) отфильтровываются окном стабильности.

#### D3. Слайды: плато и builds

- Кандидат = **последний кадр плато** (анимации доиграли, bullet-build финален),
  но ≥ 1–2 с до следующей ступеньки (не поймать transition-смаз).
- **Dedup прогрессивных builds** — вложенность бинаризованных ink-масок:
  `|prev ∧ next| / |prev| > 0.9` и ink вырос → это build того же слайда, держим
  финальную версию. (Содержательная замена старому `merge_and_dedup` c его порогом
  «10 секунд по времени».)
- Слайд со встроенным видео/демо (плато не наступает): cap кадров на режим,
  финальный выбор — за VLM QC.

Выход D: `Candidate {ts, regime_type, source: raw_frame | board_model, score}`,
~20–60 штук на 1.5 ч.

### E. Качественная выемка стопкадров

Отобранный ts — это *момент*; кадр к нему выбирается отдельно:

1. Точечный accurate-seek `ffmpeg -ss` в full-res, окно ±2 с на нативном fps;
   внутри окна — кадр с максимальной резкостью (variance of Laplacian) и
   минимальным motion; I-frames выигрывают автоматически (нет P-frame смаза).
2. **Доска**: отдаётся композит из background model (человек стёрт) +
   «whiteboard cleanup» (деление на размытый фон → фон белеет, штрихи контрастнее),
   для мела CLAHE; опционально усреднение 3–5 выровненных стабильных кадров —
   дешёвый denoise, мел читается заметно лучше.
3. **Код**: нативное разрешение, **PNG** (JPEG-артефакты убивают мелкий текст),
   опционально кроп до `content_bbox`.
4. **Слайды**: сырой кадр плато, JPEG q90.

### F. VLM №2 — QC и подписи

Батчи ≤ 16 картинок: кадр + ts + ближайшая реплика транскрипта. JSON-mode:
`keep/drop` (мусор: смаз, mid-erase, дубль, «no signal», спикер), короткий caption,
группы семантических дублей (из группы остаётся лучший). 2–4 вызова.

### G. Привязка и экспорт

`ts → секция` бинарным поиском по интервалам structurize + монотонизация (кадры не
скачут назад по секциям). Кадр доски, копившийся несколько секций, привязывается к
секции, где «дописал». Выход стадии:

```
Frame {ts, type, path, caption, section_idx, extracted_text: None}
```

В экспорт кадры идут тем же путём, что слайды сегодня (подкаталог + вставка в
секции `конспект.md`, ключи в `structure.json`).

## 6. Трасса на примере (как это отработает)

Смешанная лекция 90 мин: 0:00–0:10 вступление у кафедры, 0:10–0:40 слайды,
0:40–1:10 доска, 1:10–1:25 live-coding, 1:25–1:30 Q&A.

1. A: 5400 кадров → сигналы (~5 мин).
2. B: 5 режимов по сигнатурам: «плоско» / «ступеньки+плато» / «edge растёт» /
   «мелкие частые диффы» / «плоско».
3. C: 1 вызов flash-lite с 5 кадрами → `speaker / slides / board(chalk, bbox) /
   code(bbox) / speaker`.
4. D: слайды → 18 плато, после build-дедупа 12 кандидатов; доска → ink-кривая с
   двумя стираниями → 5 кандидатов («дописал» ×3, пред-стирание ×2); код (передекод
   15 мин на 4 fps) → 4 точки остановки, из них 2 пары «код+вывод»; спикерные
   режимы → 0 кандидатов. Итого 23.
5. E: 23 точечных seek'а; доска отдаётся из background model + cleanup.
6. F: 2 вызова → 2 дубля слайдов и 1 смазанный кадр выброшены, 20 кадрам написаны
   подписи.
7. G: кадры легли в секции по таймкодам; Q&A-секции пустые.

Итог: 20 кадров, ~10 мин работы CPU, 3 VLM-вызова ≈ 30 картинок ≈ 0 ₽ на BYOK.

## 7. Экономика VLM

~60–100 картинок на лекцию суммарно (C + F), картинка ≤ 512px ≈ 258 ток. →
~30–40k input + ~3k output. На `gemini-3.1-flash-lite`:

- **BYOK free**: 3–6 вызовов из 500–600 RPD — ничтожно; RPM 15 не ограничивает.
- **Платно (контроль)**: при $0.25/M in, $1.50/M out → **≈ $0.010–0.015 за
  лекцию** (сверено 2026-07-05).
- Fallback-модели стадии — обычный список `LLM_MODELS_*` с `ModelCooldown`.

## 8. Скорость (1.5 ч видео, 4 vCPU без GPU)

| Этап | Оценка | Обоснование |
|---|---|---|
| A: decode 1 fps + сигналы | ~5–6 мин | h264 720p decode ~500 fps на 4 vCPU → 162k кадров ≈ 5.4 мин; сигналы дешевле декода |
| B: сегментация | секунды | numpy по 5400 векторам |
| D: передекод code-режимов 3–5 fps | ~1–2 мин | декодируются только их отрезки |
| C+F: VLM 3–6 вызовов | ~1–2 мин | латентность 5–20 с, частично параллельно |
| E: 20–60 точечных seek | ~1 мин | accurate seek ~1–2 с |
| **Итого** | **~8–12 мин** | параллельно со structurize → wall-clock прирост меньше |

Резервы: первый проход по keyframes (`-skip_frame nokey`) + полный декод только
активных сегментов (для слайдовых лекций режет этап A в разы); VP9/4K декод
медленнее ×1.5–2 — укладывается с резервом.

## 9. Edge cases

- Ручная камера / панорамы / зум → режим `camera`: разреженный отбор, всё через QC.
- Автофокус/экспозиция гуляют → ink по градиентам + нормализация освещения.
- Доска и проектор в одном кадре → регионы из C, на каждый ROI своя политика.
- PiP-вебка спикера → box с постоянным motion, гейт background model маскирует.
- Слайды со скриншотами кода vs live-coding → тай-брейкер: слайды не печатают.
- Операторские склейки (спикер ↔ экран) → границы режимов; спикерные куски пустые.
- Стёр-и-сразу-пишет, частичные стирания → гистерезис порога стирания.
- Пустые/чёрные кадры, «no signal» → гистограммный фильтр + QC.
- Слайд мелькнул < 1 с (реже 1 fps) → пропустим; осознанный компромисс v1.
- Кадр доски накрывает несколько секций → привязка к секции «дописал».
- Q&A без визуала → ноль кадров (норма по договорённости).

## 10. Надёжность и деградация

- VLM недоступен / free tier исчерпан → классификация остаётся по временным
  сигнатурам B, QC пропускается: кадры чуть грязнее, но стадия работает.
- Стадия кадров **никогда не роняет задачу** (философия `no_slides`): любое её
  исключение → лог + конспект без кадров.
- Усечение выборки: жёсткий cap кандидатов (защита от патологий вроде таймлапса).

## 11. Интеграция в lecturelog-core

- Новый пакет `lecturelog/infrastructure/frames/`.
- `PipelineStage.VIDEO_SLIDES` и usage-поле `video_slides` уже существуют (оставлены
  ради истории) — переиспользуются; `UsageAccumulator.record_llm("video_slides", ...)`
  готов.
- Порт `SlideProvider` расширяется: элемент результата → `(path, timestamp | None,
  caption | None, extracted_text | None)`. Документные слайды: `timestamp=None`,
  старый LLM-матчинг. Видеокадры: привязка по таймкодам, матчинг не нужен.
- VLM — через существующий `LlmClient` (форс BYOK, `ModelCooldown`), модели —
  `LLM_MODELS_VIDEO_SLIDES` (flash-lite первым), effort low, JSON-mode.
- Пороги (ε, проценты ink, окна стабильности, K гейта) — конфиг с дефолтами;
  калибровка на 3–5 реальных лекциях разных типов.
- Зависимости: OpenCV (headless) + numpy; ffmpeg уже в образе.
- Тесты: **синтетические видео** (PIL + ffmpeg рисуют «доску с накоплением и
  стиранием», «ступеньки слайдов с builds», «печать с курсором и скроллом») →
  детерминированные юниты сигналов и политик; VLM мокается. Это главный инструмент
  TDD для стадии D.

## 12. Точки расширения под guide-режим (отдельный дизайн, позже)

«Видео → текстовый гайд» (настройка софта/VPN-ноды, реальный мир) **инвертирует
роль кадров**: критичный контент (команды, значения полей) часто есть только на
экране и отсутствует/искажён в транскрипте (Whisper калечит `wg-quick up wg0`).
Чтобы потом не переделывать контракты:

1. В контракте кадра уже есть `extracted_text` (в конспекте — `None`; в guide
   VLM дословно достаёт команды/конфиги с ключевых кадров — +1 батч-вызов).
2. «Кадры не влияют на структуру» — свойство режима конспекта, НЕ инвариант порта:
   guide подаёт содержимое кадров в структуризацию/рендер.
3. Задел API: `output_mode: summary | guide` (в v1 не реализуется).
4. Screencast-туториалы = code/terminal-режим as is; реальный мир = новый режим
   «действие»: сегментация шагов по транскрипту + лучший кадр в окне шага
   (движение стихло, руки не перекрывают объект) — «дописал» для трёхмерного мира.

## 13. Риски и критерии приёмки

Риски: (а) надёжность bbox от flash-lite — есть fallback на полный кадр;
(б) калибровка порогов — закладывается конфигом + синтетика; (в) экзотические
записи (таймлапсы, вертикальное видео) — cap + QC.

Критерии приёмки v1 (на 5 реальных лекциях, по одной на тип + смешанная):

- ≥ 90 % «очевидных» визуальных состояний (слайд/заполненная доска/финальный код)
  попали в выдачу;
- ≤ 10 % мусора после QC;
- runtime стадии ≤ 15 мин на 1.5 ч видео (4 vCPU);
- расход VLM ≤ 2 ¢ по платному прайсу (факт — на BYOK бесплатно).
