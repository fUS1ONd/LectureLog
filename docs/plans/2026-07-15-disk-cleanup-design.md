# Автоматическая очистка диска LectureLog — дизайн

Дата: 2026-07-15. Статус: реализован первый этап — безопасная очистка scratch
успешных S3-задач. TTL-sweeper, очистка Docker и серверная автоматизация пока
остаются будущими этапами.

## 1. Контекст инцидента

На VPS корневой раздел размером 38 ГБ заполнился до 93 % (34 ГБ занято,
2.7 ГБ свободно). Разбор показал:

- 13.74 ГБ занимали dangling Docker-образы прошлых сборок `lecturelog-core` и
  `lecturelog-web`;
- 961 МБ занимал `/app/data/<task_id>` одной уже завершённой задачи core;
- около 2 ГБ занимали сборочные и пользовательские кэши;
- постоянное хранилище MinIO с лекциями занимало только 1.3 ГБ и не являлось
  причиной инцидента.

После ручной безопасной очистки заполнение снизилось до 49 %. Данные MinIO,
PostgreSQL и активные Docker-образы не удалялись.

Этот дизайн предотвращает повторение двух причин, которыми владеет LectureLog:

1. утечки локального scratch задач core;
2. накопление старых Docker-образов после обновлений dev-канала.

Очистка общесистемных кэшей (`apt`, пользовательские Go/pip/uv-кэши) в scope
LectureLog не входит.

## 2. Цели и инварианты

Цели:

- после терминального завершения задачи локальные промежуточные файлы не живут
  бессрочно;
- падение процесса или VPS не оставляет вечные orphan-каталоги;
- старые Docker-образы очищаются автоматически и с ограниченным сроком хранения;
- нехватка диска обнаруживается до отказа обработки лекций;
- все действия наблюдаемы по логам и пригодны для ручного dry-run/аудита.

Жёсткие инварианты:

- никогда автоматически не вызывать `docker volume prune`;
- никогда не удалять MinIO volume, PostgreSQL volume, `uploads/` или
  `results/` этим механизмом;
- никогда не удалять workdir задачи в статусе `pending` или `processing`;
- результат `done` считается сохранённым только после успешной загрузки всех
  объектов в MinIO и сохранения `result_path` в БД;
- сбой очистки не должен менять успешную задачу на `failed` и не должен скрывать
  исходную ошибку пайплайна;
- контейнер API не получает `/var/run/docker.sock` и не управляет Docker host.

## 3. Что существует сейчас

- `WORK_DIR` по умолчанию равен `/app/data` и находится в writable layer
  контейнера API.
- На каждую задачу создаётся `/app/data/<task_id>`.
- Пайплайн скачивает туда исходник и создаёт аудио, кадры, нарезанные секции и
  экспорт. После загрузки `export/output` в `results/<task_id>/` worker удаляет
  workdir успешной S3-задачи; SRT сохраняется в том же постоянном результате.
- Временные каталоги `results_tmp` для скачивания результата уже очищаются через
  `BackgroundTask`/`finally` и не являются найденной утечкой.
- При старте `processing` задачи переводятся в `interrupted`, но их workdir не
  очищается.
- VPS обновляется через `docker compose pull && docker compose up -d`. Плавающий
  тег `:dev` оставляет предыдущие образы dangling.
- `Task.updated_at` сейчас переносится из доменной модели в БД, но `_set()` не
  обновляет его. Использовать это поле как TTL-источник до исправления нельзя.

## 4. Очистка scratch задачи в приложении

### 4.1. Основной путь: немедленно после `done`

Владельцем lifecycle workdir становится `PipelineWorker`, потому что именно он
владеет `PipelineJob.work_dir` и видит окончание `PipelineService.run()`.

Последовательность успешного пути:

1. pipeline формирует результат локально;
2. каждый файл результата успешно загружается в MinIO;
3. задача сохраняется как `done`, `result_path=results/<task_id>/`;
4. терминальный webhook выполняется best-effort по существующим правилам;
5. `PipelineService.run()` возвращает управление worker;
6. worker best-effort удаляет только каталог конкретного задания
   `<WORK_DIR>/<task_id>`;
7. успех или ошибка удаления логируются с `task_id`, путём и освобождённым
   объёмом, если его удалось посчитать без дорогого обхода.

Удаление выполняется после фиксации `done`, поэтому сбой `rmtree` не влияет на
результат. Повторное удаление идемпотентно (`missing_ok`/`ignore_errors` с явным
логированием реальной ошибки).

Перед удалением требуется защита пути:

- имя каталога строго равно ожидаемому `task_id` (32 hex-символа);
- `resolve()` каталога обязан быть непосредственным потомком `WORK_DIR.resolve()`;
- запрещено удалять сам `WORK_DIR`, `results_tmp`, symlink или произвольный путь
  из внешнего ввода.

### 4.2. Ошибки пайплайна

Для `failed` scratch полезен при диагностике, но не должен храниться бессрочно.
Выбран компромисс:

- `done`: удалить сразу;
- `failed`: сохранить на 24 часа;
- `interrupted`: удалить после старта приложения, когда статус уже зафиксирован в
  БД; возобновления задачи сейчас нет, поэтому scratch не используется;
- `pending`/`processing`: не удалять.

При переходе в `failed` worker создаёт в каталоге служебный marker с терминальным
статусом и UTC-временем. Marker пишется атомарно и не содержит секретов или текста
ошибки. TTL считается по marker, а не по mtime произвольных медиафайлов.

Для `interrupted` marker создаётся startup-reconciler после успешного перевода
статуса в БД. Допустимо удалять такой каталог в том же проходе: после рестарта
текущая архитектура всё равно не умеет продолжать задачу.

### 4.3. Страховочный sweeper

В процессе API работает один фоновый sweeper:

- первый проход — после инициализации БД и `mark_stale_as_interrupted()`;
- следующие проходы — раз в час;
- параллельные проходы в одном процессе запрещены lock-ом;
- ошибка одного каталога не останавливает обработку остальных.

Алгоритм для каждого непосредственного дочернего каталога `WORK_DIR`:

1. пропустить зарезервированный `results_tmp`;
2. провалидировать имя и безопасный resolved path;
3. получить задачу из repository;
4. `pending`/`processing` — всегда оставить;
5. `done` — удалить как orphan успешного пути;
6. `failed` — удалить, только если terminal marker старше TTL;
7. `interrupted` — удалить;
8. строки в БД нет — удалить только при наличии marker либо после отдельного
   orphan TTL (по умолчанию 24 часа), чтобы не состязаться с созданием задачи.

Один проход ограничивается каталогами верхнего уровня и не следует symlink.
Sweeper не ходит в MinIO и ничего не решает по совпадению S3-префиксов.

### 4.4. Конфигурация

Предлагаемые параметры:

```env
WORK_DIR=/app/data
WORK_DIR_CLEANUP_ENABLED=true
WORK_DIR_FAILED_RETENTION_HOURS=24
WORK_DIR_ORPHAN_RETENTION_HOURS=24
WORK_DIR_SWEEP_INTERVAL_MINUTES=60
```

Значения валидируются в общем config-слое; отрицательные TTL запрещены. Для
локальной разработки очистку можно выключить. Production/VPS default — включено.

Отдельно в реализации нужно исправить семантику `Task.updated_at`: обновлять поле
при каждом repository update или на уровне БД. Sweeper от него не зависит, но
поле должно соответствовать своему имени и пригодится мониторингу.

## 5. Host-level очистка Docker

Docker cleanup не запускается из API: доступ к Docker socket дал бы приложению
root-эквивалентные права на VPS.

В репозитории core хранятся deployment-артефакты:

```text
deploy/systemd/lecturelog-docker-prune.service
deploy/systemd/lecturelog-docker-prune.timer
deploy/scripts/lecturelog-docker-prune.sh
```

Они устанавливаются на конкретный LectureLog VPS вручную или отдельной командой
деплоя; к `nodes-infrastructure` и VPN-нодам отношения не имеют.

Timer запускается еженедельно с jitter (`RandomizedDelaySec`) и выполняет:

```bash
docker image prune -f --filter "until=168h"
docker builder prune -f --filter "until=168h"
```

Ограничения скрипта:

- используется именно `image prune` без `-a`: удаляются dangling-образы, а не все
  неиспользуемые tagged-образы;
- обязательно задан `until=168h`, чтобы оставить окно для диагностики/rollback;
- запрещены `docker system prune`, `docker volume prune` и `--volumes`;
- перед очисткой логируются `df -h /` и `docker system df`, после — те же значения
  и exit codes;
- если Docker daemon недоступен, unit завершается с ошибкой, но не пытается
  перезапускать или останавливать сервисы;
- service имеет lock, чтобы не пересечься с ручным/деплойным запуском того же
  скрипта.

Post-deploy prune сразу после `compose up` не является единственной защитой:
не каждый deploy доходит до последнего шага. Systemd timer остаётся источником
гарантированной периодической очистки. В будущем deploy может дополнительно
вызвать тот же идемпотентный скрипт после health-check.

## 6. Логи и контроль свободного места

### Docker logs

Для сервисов VPS в `deploy/compose.vps.yml` задаётся ротация `json-file`:

```yaml
logging:
  driver: json-file
  options:
    max-size: "50m"
    max-file: "3"
```

Лимит применяется ко всем постоянным контейнерам core. Это превентивная мера:
в инциденте Docker-логи занимали мало места.

### Admission check для новых задач

Перед сохранением большого multipart upload и перед enqueue новой задачи API
проверяет свободное место файловой системы `WORK_DIR`.

Предлагаемые пороги:

- soft warning: свободно меньше 20 % или 8 ГБ;
- hard stop: свободно меньше 10 % или 3 ГБ.

На hard stop новая задача получает явный `503 Insufficient local disk space` и
не ставится в очередь. Уже выполняющиеся задачи не убиваются. Проверка является
последним предохранителем, а не заменой cleanup.

Порог должен учитывать максимум одновременных задач: одна видео-задача в
наблюдаемом случае создала scratch примерно в 4.5 раза больше исходного файла.
До появления точной модели резервирования консервативный абсолютный порог 3 ГБ
обязателен.

### Наблюдаемость

Минимум для первой реализации — структурированные логи:

- `workdir_cleanup_success{task_id, status}`;
- `workdir_cleanup_failed{task_id, status, reason}`;
- итог sweeper: scanned/deleted/skipped/freed_bytes;
- до/после Docker prune: filesystem used %, image reclaimable bytes.

Если в проекте появятся метрики, те же значения экспортируются как gauges/counters.
Отдельный alert рекомендуется на 80 % и 90 % заполнения корневого раздела.

## 7. Границы ответственности данных

| Данные | Владелец очистки | Политика |
|---|---|---|
| `/app/data/<task_id>` | core worker + sweeper | `done` сразу; `failed` через 24 ч; `interrupted` после рестарта |
| `/app/data/results_tmp` | API result endpoints | уже чистится после ответа/ошибки; sweeper не вмешивается |
| MinIO `results/<task_id>/` | `DELETE /tasks/{id}` | не трогать disk-pressure cleanup-ом |
| MinIO `uploads/<uuid>/` | `DELETE /tasks/{id}` | не трогать disk-pressure cleanup-ом |
| MinIO `results-tmp/` | endpoint + ILM + DELETE | существующая краткоживущая политика |
| PostgreSQL volume | PostgreSQL/backup policy | никогда не prune |
| dangling Docker images | host systemd timer | старше 7 дней |
| tagged rollback/release images | оператор/release policy | автоматически не удалять в v1 |

## 8. Отвергнутые варианты

### `docker system prune -a --volumes`

Слишком широкий blast radius: может удалить неактивные release-образы и volumes с
данными. Для автоматического запуска запрещён.

### Монтировать Docker socket в API

Компрометированный API получит контроль над всем хостом. Очистка Docker остаётся
host-level задачей.

### Чистить workdir только по возрасту файлов

Можно удалить долгую активную обработку или свежий каталог при рассинхронизации
часов. Статус задачи является главным условием, marker — только TTL терминального
состояния.

### Хранить `/app/data` в tmpfs

Видео scratch может занимать гигабайты. На текущем VPS это превратит disk pressure
в memory pressure/OOM и потому не выбирается.

### Полагаться только на пересоздание контейнера

Writable layer действительно исчезает при замене контейнера, но обработка может
создать гигабайты между деплоями, а неуспешный deploy не гарантирует замену.

### Удалять scratch только через `DELETE /tasks/{id}`

Платформа может долго хранить готовую задачу, а локальные файлы после публикации
результата уже не нужны. Lifecycle результата в MinIO и lifecycle scratch должны
быть независимы.

## 10. Проверка и критерии готовности

Unit/integration:

- после успешного pipeline result существует в fake S3/repository, а workdir
  отсутствует;
- ошибка удаления workdir не меняет `done` и логируется;
- failed-каталог младше TTL сохраняется, старше TTL удаляется;
- processing/pending не удаляются независимо от возраста;
- interrupted после startup удаляется;
- неизвестный свежий каталог сохраняется, старый orphan удаляется;
- `results_tmp`, symlink, malformed task id и путь вне `WORK_DIR` не удаляются;
- два одновременных sweep не выполняются;
- `updated_at` реально меняется при обновлении задачи.

Deploy:

- prune unit в тестовом режиме не содержит `--volumes`, `system prune` или
  `image prune -a`;
- активные контейнеры и их образы остаются на месте;
- MinIO/PostgreSQL volumes до и после имеют те же имена и данные;
- dangling-образ моложе 7 дней остаётся, старше 7 дней удаляется;
- повторный запуск идемпотентен;
- journal содержит объём до/после и понятный exit status.

Приёмка на VPS:

- завершить тестовую видео-задачу и убедиться, что `results/<task_id>/` доступен,
  а `/app/data/<task_id>` удалён;
- искусственно оставить failed/interrupted каталоги и проверить политики TTL;
- выполнить timer вручную, проверить health всех контейнеров и скачать результат;
- через неделю убедиться, что writable layer API не растёт от завершённых задач,
  а dangling images не старше заданного окна.
